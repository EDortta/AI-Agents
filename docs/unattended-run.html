Operating mode

Running unattended

An agent can work a queue of issues overnight, on a schedule, with nobody watching. The hard part is not making it continue. It is making it stop.

What this mode is

An unattended run is an agent that picks issues off a queue and works them while you sleep: implement, review, record, and stop. The kit contract for it is .docs/workflows/unattended-run.md, which an agent must load before arming anything that runs without supervision, and before reviewing anything that already is.

The kit does not ship a pipeline. It ships the rules such a pipeline has to satisfy — the stop conditions, the ceilings, the escalation protocol, the report. The mechanism is yours to build, because every mechanism reviewed so far broke somewhere the rules did not.

Why the stop condition is the whole feature

On 13–14 August 2026 two pipelines ran for about twelve hours and closed zero issues. One repeated the same review cycle roughly a hundred times. The other refused to start every ten minutes for hours, blocked by leftovers from a dead unit, and never said so. Both looked healthy from outside the entire time.

Nothing there was a model failure. Every instruction specified how to continue and none specified when to give up.

Suspend

A known transient condition with a written resume rule next to it — the window closed, the night budget is spent. Without such a rule, the correct outcome is a fault.

Fault

Confidence in the run's own state is gone — a boundary was crossed, the branch is failing its own checks, the tree is dirty from an unknown source. It never resumes on its own.

No progress

A fault, not a suspension. N issues in a row that consumed real work and closed nothing is evidence the work model is not working tonight. That needs a human, not another night.

Does running at night make it cheaper?

Not by itself. The Anthropic API has no time-of-day pricing: a token costs the same at 03:00 as at 15:00. If you have heard otherwise, the claim being remembered is almost certainly the Batch API discount, which is about how you send the work, not when.

What does move the bill, in the order the money actually sits:

LeverEffectFits an unattended run?
Stopping early Unbounded. This is the biggest number on the page. Always. A run that gives up at 02:00 instead of billing until 08:00 saves more than every other line in this table combined. In the incident, twelve hours of spend bought nothing.
Prompt caching Cache reads bill at roughly a tenth of the input price. A write costs 1.25× at the default 5-minute TTL and 2× at the 1-hour TTL an overnight run with idle gaps between issues would actually want — which also moves break-even from two requests to three. Yes, and it is where the money is. An agentic call re-sends its whole context on every turn: one measured call showed 7.1M cached input tokens against 68k of output, and still cost USD 6.86. A ceiling on output tokens bounds nothing.
Model tiering About 2.5× between the current tiers — Opus 5 at $5/$25 per MTok against Sonnet 5 at $2/$10. Name the exact models when you size this: the gap moves between generations, and a rate remembered from the previous one is not the rate you will pay. Yes — an expensive model for analysis and review, a cheaper one for implementation. Report cost by phase and by model: nothing on this page tells you what a review round costs, so only your own numbers can say whether the cheaper implementation model is paying for itself or just buying extra rounds at the expensive model's price.
Batch API 50% off input and output, results within 24 hours. Rarely, and not for the agent loop. Batch takes independent, non-interactive requests submitted up front. An agent that reads a file, decides, edits, and reads again cannot be expressed that way. It fits the parts around the loop — bulk classification, summarising a night's logs — not the loop itself.

What the night actually buys you is your own hours, plus an uninterrupted window that no one will need the machine during. Treat any cost saving as coming from the ceilings and the stop conditions, not from the clock.

The ceilings that have to exist

Every one of these is in the contract because its absence has already cost money.

  • Cap every call, including the implementation call. In the incident the expensive call was implementation, not review.
  • Cap the input, not just the output and the turn count. See the 7.1M-cached-against-68k envelope above.
  • Cap by count as well as by money. Some providers report no cost at all; when money is unavailable the count is the only ceiling that binds.
  • Refuse before spending, not after. A call that cannot be paid for is refused at admission.
  • A cancelled or failed call is not free. Record what it used, as exposure, never as zero.
  • Cap the review rounds. Two per object; there is no third. And detect the cycle, not just the repetition — A→B→A is the common shape.
  • Cap the campaign, not only the night. A night limit multiplied by the nights nobody looks is not a limit.

Before you arm anything

# The operator answers these once, and they are stored and echoed back
#   - which repositories, and which paths inside them may change
#   - which model for which phase, by exact name
#   - every ceiling: per call, per issue, per round, per night, per campaign
#   - concurrency, of model calls and of local builds and test suites
#   - the window, checked against the host's maintenance calendar
#   - the notification channel, and how delivery is confirmed
#   - what review must pass before work reaches the integration branch

# Then prove each brake by breaking it on purpose, and kill the process at
# every boundary to show that nothing is duplicated and nothing is lost.

An untested brake does not exist. Whatever was not exercised end to end has to be stated as such, in writing, before the first unattended night.
